# 16-draft CPU/GPU heterogeneous experiment

Completed: all three methods finished 16/16 requests with no RPC errors. See [中文结果报告](RESULTS.zh.md), [full statistics](RESULTS.md), and [latency plot](latency_comparison.png). FastSD matches Standard SD on 16/16 output sequences; SpecEdge matches 15/16. Host load differed substantially between methods.

Requested comparison: Standard SD, FastSD, then single-chain SpecEdge.

- node1: 8 independent Qwen3-1.7B CPU FP16 drafts, fixed gamma=100.
- node3: 8 independent Qwen3-1.7B CPU FP16 drafts, fixed gamma=20.
- Each draft uses one physical core and one compute thread, with NUMA-local memory. Placement is selected once from a one-second core utilization sample and reused across methods.
- Target: Qwen3-32B FP16 on gpunode2 physical GPU3 (RTX A6000, 48GB). GPU weight budget 34GiB, remaining weights use CPU offload. No quantization. Other GPUs already had unrelated processes.
- Both native methods use padded KV batching, batch_size=8, token_budget=512. Gamma adaptation is disabled on both clients and Target.
- Dataset: first 16 GSM8K questions; original even indices on node1 and odd indices on node3, one request per worker. Same mapping for all methods. Non-thinking chat template, greedy verification, EOS enabled, max_new_tokens=256.
- No measured warmup requests. A separate 4-token smoke request validates the loaded Target and remote protocol before the measured run. Model loading is excluded from request latency.
- CPU commands execute through tmux 6:0.0 (node1) and 6:0.1 (node3); GPU commands use tmux session8. Direct CPU-to-GPU TCP timed out, so the existing SSH sessions provide loopback-only reverse forwarding: CPU28624 to coordinator18624 and CPU28625 to Target18625. All methods use the same route.
- The coordinator binds only GPU-node private address10.66.0.5, authenticates requests, restricts client IPs and fixed run names, and records an overall completion window on one clock. FastSD clock calibration is serialized across both CPU nodes before a shared request barrier.

## Metrics

Report overall and per-node request count, TTFT(s), TPOT(ms), E2E(s), mean/p50/p95, retained output tokens, weighted draft acceptance, verify HTTP latency, and output consistency across methods.

Native TTFT starts immediately before session initialization and ends when the first verified token block becomes visible. TPOT is `(E2E - TTFT) / (generated_tokens - 1)`, not an independently observed streaming interval. Native completion includes waiting for outstanding proactive work. Coordinator throughput includes post-load startup/calibration and worker completion; host-local monotonic clocks are never subtracted across machines.

## Artifacts

`manifest.json` freezes configuration and source hashes. `source/` is the inference snapshot. `standard/` and `fastsd/` hold each Target and node's raw output; `smoke-*` are separate validation runs. `setup-attempts/` retains unsuccessful startup diagnostics. `results.json`, `results.csv`, and `RESULTS.md` are generated by `summarize.py` after the measured runs. SpecEdge implementation/configuration will be archived alongside its results.

## Interpretation

This is one small paired experiment on shared CPU hosts. node3 already had substantially higher host load before the run. CPU model/runtime versions differ between nodes; node identity and gamma vary together. The Target includes CPU weight transfer, so results are specific to this capacity-limited deployment and cannot establish performance for a fully GPU-resident32B model. Truncated GSM8K output is not an accuracy evaluation.
