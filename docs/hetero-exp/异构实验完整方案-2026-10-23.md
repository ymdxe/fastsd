## 一、论文实验要回答的问题

| 编号 | 问题 | 主要证据 | 结论应保留的边界 |
|---|---|---|---|
| RQ1 | 多客户端异构部署下，FastSD 的总体表现如何？ | 16/32/64 规模下四方法的 TTFT、TPOT、E2E、吞吐、能耗 | 不预设所有场景都更快 |
| RQ2 | 硬件和模型异构各自产生什么影响？ | 硬件×模型交叉实验、按客户端类别的等待分布 | 不能把两机共享资源效应全部叫作设备速度差异 |
| RQ3 | 不同 γ 是否影响调度收益？ | 固定 γ、相同均值的混合 γ、能力映射 γ | 区分 γ 策略收益和调度器收益 |
| RQ4 | 多队列、异构优先级、WRR、KV 预取分别贡献什么？ | 同一执行后端的逐项消融 | 跨引擎系统比较不能单独归因于某一模块 |
| RQ5 | 收益在高负载、网络变化、慢客户端和 KV 压力下是否保持？ | 负载曲线、分组尾延迟、压力实验 | 报告退化区间与超时，不只报成功请求 |

核心判断采用“同负载下时延/能效是否改善”和“同 SLO 下可持续吞吐是否提高”。不预先填写加速倍数；预实验后、正式测试前冻结主要指标和实用改善阈值。

D1 = Qwen3-1.7B；D2 = Qwen3-1.7B-Base。两者都是名义 1.7B 档，以不同 checkpoint 构成模型异构；D2 的 tokenizer 已通过本轮核验。

| N：draft 实例总数 | node1-D1 | node1-D2 | node3-D1 | node3-D2 | node1/node3 总实例 |
|---:|---:|---:|---:|---:|---|

不能让 node1 只用 D1、node3 只用 D2，否则硬件和模型效应无法区分。各类型接收同样的数据集/长度分布；跨重复轮换请求到 worker 的分配，防止难题恰好集中在某一种类型。

D2 完成权重推理及统一停止规则验收前，先用 D1 完成纯硬件异构预实验；将这些数据标为 D1-only，不将其写成双模型实验。

### C. CPU 与内存控制

- 起始方案：每 worker 绑定 1 个独立物理核，模型计算线程数固定为 1；约束 PyTorch、OpenMP、MKL 等隐式线程扩张，并记录实际线程数。
- 按物理 core ID 选核，不把同一核的两个 SMT 线程视为两颗独立核。各方法使用完全一致的 cpuset 与 NUMA 内存策略。
- node1 的 32-worker 配置需保留其余核给系统、网络和采样器；不要在主实验突然改为每 worker 2 线程导致超额订阅。
- 两机采用预先定义的均衡 NUMA 分布，记录跨 NUMA 访问；1/2/4 线程效率比较仅做单独资源敏感性实验。
- 容量估算：D1/D2 都为名义 1.7B、配置绑权的模型；按约 1.72B 独立参数估算，BF16 约 3.44 GB/实例，每机 16+16 份约 110.1 GB，尚不含 KV、激活、分词器和进程开销；FP32 约翻倍。checkpoint 可能保存额外/重复权重，实际加载 RSS 取决于加载与绑权实现，必须实测。
- 单实例能启动不代表 32 实例能稳定运行。先测单份/多份模型的 RSS、带宽与输出速度；禁止用 swap 支撑主性能实验。
- CPU dtype 以共同可运行且验证正确的设置为准；不能默认两代 CPU 的 BF16 都有同样加速。

### D. Qwen3-32B 的云端容量

32B 级模型仅 BF16 权重就约需 64 GB（粗估），还需 KV cache、工作区和运行时余量。旧 Llama 7B 的单卡经验不能直接外推到 32B。

正式先选择一种所有基线都支持的部署：足够显存的单卡，或通过实测验收的相同多卡布局。若必须量化，四方法使用相同 Target 权重/量化配置，并重新验证 Target 数值行为、varlen 路径与 SpecEdge；不能只量化某一种方法。

后续验收顺序（tokenizer 本轮已核验，部署环境变化时重查）：
- 复用上述冻结 ID/revision；正式权重与 tokenizer 使用同一模型版本，记录精度与实际加载配置。
- 比较完整 token→ID 映射、特殊 token、BOS/EOS/PAD、词表范围、归一化及编码规则；词表大小相同不是充分条件。
- 使用代码、数学、中文/英文、特殊符号等真实输入检查同一 prompt token 序列。
- Target 的 prompt 模板先生成并冻结；同一请求在所有方法中使用相同 token ID。不能让每个 draft 用自己的聊天模板重新解释 prompt。
- 检查 D2 在所有基线的 draft 推理路径能工作；当前云端 varlen 的 Qwen3 支持不代表任意约 2B 架构都可用。
- 先 greedy 小样本逐 token 对照，再验收随机采样的拒绝采样逻辑与质量。随机采样不同算法即使种子相同，也不要求逐样本输出完全相同。
- 若 tokenizer 不兼容，需要跨 tokenizer 推测算法或专门映射，是另一项方法工作；不能靠直接复用 token ID “凑合运行”。

### B. 数据集：覆盖三种任务

| 数据集 | 任务 | 正式质量评测 | 性能工作负载 | 解释范围 |
|---|---|---|---|---|
| HumanEval | 代码生成 | 冻结官方任务列表，pass@1 | 保存 prompt 与 token 长度；按固定顺序/种子重放 | 质量执行在隔离评测环境进行 |
| GSM8K | 数学推理 | 冻结 test split，按确定的答案提取规则算准确率 | 可先取固定 256 条调试；正式使用冻结列表 | 不用测试结果调 γ/调度超参数 |
| MT-Bench | 通用指令/对话 | 可另做完整多轮质量评估 | 主性能使用第一轮 prompt，命名 MT-Bench-first-turn | 不能将第一轮性能实验叫作完整 MT-Bench 质量评分 |

数据来源：[HumanEval](https://github.com/openai/human-eval)、[GSM8K](https://github.com/openai/grade-school-math)、[MT-Bench](https://github.com/lm-sys/FastChat/tree/main/fastchat/llm_judge)。实际样本量以冻结文件和过滤日志为准。

另建 MixTrace，三种任务按 1:1:1 请求数混合，用于异构、消融和负载实验。每个请求保存 source_id、dataset、prompt、token IDs、输入长度、输出上限、开环计划到达时间或闭环释放规则、分配的 worker 类型和种子；记录数据版本、过滤规则和 workload hash。

### C. 三种数据用途分离

- Calibration：单独的校准请求，用于性能档案、γ、tree budget/depth、token budget、SLO 与超时设置。若从测试任务中划出，必须明确留出并不再用于最终质量评分；更优先采用训练集或另建的公开开发集。
- Performance trace：最终性能重放。可重放同一原题形成长时间流，重复项用 replay_id 标识，不当作新的独立题目；跨请求前缀缓存默认关闭，防止重放产生缓存优势。
- Quality set：保持原题和自然停止，避免为了输出长度而修改参考答案或测试用例。性能重放次数不能扩充质量样本量。

### D. 输入长度和输出长度

- 主任务性能：固定共同的 max_new_tokens=256，EOS 正常生效；记录真实完成长度、截断率及停止原因。该上限只定义系统工作负载，不代表模型的最佳答题质量。
- 独立质量评测：按任务需要设置共同且足够的上限，预实验查看截断；所有方法采用同一上限和停止规则。
- 受控长度压力：输入长度目标取 128/512/2048，输出长度取 128/256/512。以固定 token 预算生成的压力数据必须单独标为长度微基准，不与真实任务准确率混合。
- 自然数据按实测长度分桶，建议 ≤128、129–512、>512；若自然数据长请求不足，额外构造有语义的长上下文性能请求，记录真实 token 数。不能无说明地填充或截断题目后继续声称是原始质量测试。

### E. 采样与 thinking

主性能建议统一采用 non-thinking，Target 的 temperature=0.7、top_p=0.8、top_k=20、min_p=0；这与 [Qwen3 官方 non-thinking 建议](https://huggingface.co/Qwen/Qwen3-32B#best-practices)一致。草稿采样分布及稀疏概率支持集另记，拒绝采样必须使用实际生成候选的 q。

所有数据集冻结 enable_thinking=False 后的实际输入，不能只在 MT-Bench 开关关闭。最小正确性验收单列 greedy；若某基线当前只支持 greedy，共同 greedy 主实验也可作为明确限定的实验轨，但不可混用 greedy 与随机采样结果。Thinking 模式放在可选扩展，不与主结果拼接。

## 5.1.3 Baselines：四种主方法与控制条件

推荐论文主图使用以下四种方法：

| 图例 | 定义 | 配置边界 | 目的 |
|---|---|---|---|
| Target-only AR | 只有云端 Qwen3-32B 逐 token 解码 | 同客户端请求入口/网络、相同 Target 资源和采样语义，使用合理批处理 | 衡量云边协同相对直接云端服务的收益 |
| Standard SD | CPU draft + 云端验证，常规顺序投机解码 | FastSD 公共后端；无 FastSD 多队列/预取和主动草拟；主 γ=4 | 衡量完整 FastSD 相对基础投机解码的收益 |
| SpecEdge-CPU | 官方 SpecEdge 核心 + 当前 CPU 适配 | 名称固定为 SpecEdge (CPU-adapted)，锁定官方提交和适配补丁 | 对比已有云边协同系统 |
| FastSD | 完整设计 | 异构优先级、多队列、WRR/token budget、KV 预取；各开关写入 manifest | 待评价的方法 |

Standard SD 的概率保持原理参见 [Leviathan et al., ICML 2023](https://proceedings.mlr.press/v202/leviathan23a.html)。SpecEdge 方法与树结构配置参见 [官方实现](https://github.com/kaist-ina/specedge)及[论文](https://arxiv.org/abs/2505.17052)。

资源公平性：
- 所有方法使用同一个 Target、相同 GPU 集合、精度、可用 KV 容量和任务集合。闭环共享请求列表、分片与提交规则；开环共享精确的外生到达时间轨迹。
- 三种 SD 方法拥有同样的 CPU 核数、D1/D2 实例映射、网络和模型版本。
- AR 不运行 draft；图中的 N 表示“对应 N 客户端场景”，不能写它也有 N 个 draft。其边缘前端和闲置资源能耗边界另按 5.1.4 明确。
- FastSD 与 Standard SD 固定同一串行 γ；SpecEdge 是树式候选，tree depth、tree nodes budget 与 γ 不是同一个量。保留公开方法合理调参，在同一校准集与调参预算下冻结配置，同时报告实际 draft/verify token 开销。
- 若给所有方法统一候选 token 预算，这是额外预算匹配实验，不冒充各系统原生最优配置。
- 跨引擎比较披露 attention backend、批处理及环境差异；机制归因依靠同后端消融，不靠跨系统柱图。

当前仓库的默认四方法其实是 FastSD / SpecEdge-CPU / Standard SD / Draft-only。Draft-only 不保持 Qwen3-32B 的质量与输出分布，应移到附录的质量—速度参照。当前 Target-only 是本地 greedy 参考入口，正式作为主性能基线前需接入同拓扑服务与统一计时；本方案没有修改这些代码。

## 5.1.4 Metrics：测量口径

### A. 时间定义

对每请求 i，记录：
- a_i：请求释放时刻；开环为外部控制器预定到达时刻，闭环为首批 barrier 或该 worker 上一请求完成后新请求实际释放的时刻；
- s_i：worker 接受并开始处理的时刻；
- f_i：边缘消费接口首次获得非空、已经 Target 验证的输出 token 的时刻；
- l_i：最后一个确认 token 可用的时刻；
- c_i：请求真正结束的时刻，包含必要的结束处理；
- n_i：最终有效输出 token 数，不计 prompt、被拒绝候选或内部树节点。

主实验是边缘接口可用时间，不自动等于终端用户屏幕显示时间。若之后接入真实流式前端，再额外测用户可见时间；两种端点不可混写。时间间隔在同一时钟域计算，跨主机用统一控制器或校准时钟映射，禁止直接相减不同主机的 monotonic 值。

| 指标 | 定义 | 汇总 |
|---|---|---|
| TTFT | f_i − a_i，含客户端待处理积压、本地草拟、网络和云端排队 | p50、p95、均值；另记 f_i−s_i |
| TPOT | (l_i−f_i)/(n_i−1)，n_i>1 | 每请求先计算，再报 p50/p95；n_i≤1 为 NA |
| E2E latency | c_i−a_i | p50、p95、均值，另记 l_i 与 c_i 差值 |
| 请求输出速度 | n_i/(c_i−a_i) | 作为次指标，不能等同系统吞吐 |
| 系统输出吞吐 | 公共窗口内成功交付的有效输出 token 总数 / 窗口时长 | tokens/s |
| 请求吞吐 | 公共窗口内完成请求数 / 窗口时长 | requests/s |
| Goodput | 同时满足质量/完成条件和预注册 SLO 的请求数 / 窗口时长 | requests/s |

TPOT 的通用口径见 [vLLM 基准指标说明](https://docs.vllm.ai/en/latest/benchmarking/cli/)；本方案显式使用最后 token 到达时间，并另记请求结束时间。若实现只有 c_i，则须说明 TPOT 使用 (c_i−f_i)/(n_i−1) 的近似及其尾处理开销。

投机解码按块确认 token：TPOT 不代表均匀的逐 token 间隔。另记录确认块大小、块时间戳和最长无输出停顿；不能把一个确认块的耗时人为均分成“实测逐 token 延迟”。

当前代码的 ttft_ms 从 s_i 开始；负载实验需要 scheduled_ttft_ms 或由日志重算 f_i−a_i。少于 2 token 的 TPOT 不得以 0 混入平均数。不要取各 worker 的 tokens/s 算术平均作为系统吞吐。

### B. 能耗：先声明测量边界

优先同时记录以下两种边界，能够测哪种就按哪种命名：

1. 整机服务能耗：node2 + node1 + node3 在公共窗口内的墙端/PDU/BMC 能量。可以称“所测三台服务器总能耗”；未测交换机等设备时不能称完整数据中心能耗。不要再叠加这些机器的 GPU 能量，以免重复计数。
2. 组件能耗：全部 Target GPU + 三台主机可读取的 CPU package/DRAM。记录缺失域、互相覆盖的域及传感器范围；只能称“所测组件总能耗”，不能当作完整整机能耗。

GPU 优先用累计能量计数器差值；不支持时用功率采样积分。CPU 使用 RAPL 的 package 及可用的非重叠 DRAM 域，处理计数器回绕；不会按“CPU 利用率×TDP”伪造实测能耗。接口依据：[NVML](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html)、[Linux powercap/RAPL](https://docs.kernel.org/power/powercap/powercap.html)。

公式：
- E_run = 同一公共测量区间内各不重叠域的能量之和。
- J/token = E_run / 成功交付输出 token 总数。
- J/request = E_run / 完成请求数。
- 能效 = 成功交付输出 token 总数 / E_run。
- 若需要增量能耗，E_incremental = E_run − P_idle × T；同时报告原始总量、idle 测量条件与时长，不隐藏不稳定或负估计。

运行规约：
- 模型加载和 warmup 不进主能耗窗口，但可另报冷启动成本；正式窗口包含等待、被拒绝草拟、回滚、预取、重试与失败请求耗能。
- 测量窗口的起止规则对所有方法相同；固定工作量实验中各方法耗时可以不同，不能人为裁剪为只包含模型活跃片段。
- 记录所有 GPU UUID，避免 CUDA 逻辑 cuda:0 与 NVML 物理索引混淆；多卡 Target 必须覆盖全部卡。
- 组件采样建议起点为 100 ms，但以传感器实际更新周期为准，检查缺失和采样开销；提高读取频率不等于提高传感器精度。
- 正式运行尽量独占实验节点或至少隔离负载，记录后台任务；RAPL 包级能耗不能精确归因于某个进程。
- AR 主比较保留相同预留 testbed 的能耗边界，边缘无需草拟但前端运行/闲置能耗仍计入；另报“仅启用所需资源”的部署边界作为补充，避免混用分母。
- 完成率不同或系统过载时，能耗与失败率、积压量、J/SLO 合格请求一起报；不能靠丢弃困难请求获得低 J/token。

### C. 异构解释指标与正确性

必须有：各 H×D 类型的排队 p95、E2E p95、完成率、吞吐贡献；实际草拟时间、通信、云端排队、verify、KV 搬运耗时；GPU 利用率、内存峰值、预取命中/浪费；每轮实际 γ、验证/接受/丢弃 token 数。

链式 SD 接受率 = 被接受 draft token / 提交验证 draft token；不计修正 token。树式 SpecEdge 另报接受深度、验证节点数和有效输出/验证节点，不能把树节点接受率直接当作链式接受率。

公平性主报各类型相对其单客户端基线的 slowdown 与最慢类型 p95；可补充基于归一化服务率的 Jain 指数，不把异构硬件的原始 tokens/s 相等当成唯一公平目标。

Greedy 验收报告相同 Target 配置下的 token 一致性和分歧样本；随机采样报告实现验证及任务质量的区间估计，不能用“没有显著差异”证明完全等价。若要声称质量不劣，正式前规定非劣界限并给出相应置信区间。

# 5.2 Experimental Results：实验组织与绘图

## 5.2.1 总体性能与规模扩展（E1，优先完成）

主设置：T1；H1/H3=1:1；D1/D2=1:1 且交叉；N∈{16,32,64}；四方法；三数据集分别测试。FastSD/Standard SD 的固定 γ=4；SpecEdge 独立记录树预算和深度。

**工作负载 A：固定工作量、闭环运行。**
- 每个场景使用完全相同的冻结请求列表和每类 worker 任务分片，最多 C=N 个请求同时进入 worker，每 worker 一次只处理一条请求。
- 完成一个请求后处理下一条；闭环 a_i 随各方法的完成反馈确定，实际到达时间可以不同。四方法共享请求列表、分片和释放规则，不承诺共享相同的到达时间；只有 E5A 使用共同外生到达轨迹。
- 统一 barrier 开始，从第一条正式请求允许进入到全部完成/达到预定义超时结束，计算公共 makespan、总有效输出与能量。

- 小数据集可以有计划地重放以让最短正式运行足够稳定；重复次数在校准后一次冻结，跨方法/N 相同。首发建议最短运行至少 5 分钟，CPU 太慢时按实测计划时长；不是强制对每个方法运行恰好 5 分钟。

## 5.2.4 机制消融与时延分解（E4）

固定 N∈{32,64}、Hmix、Dmix、MixTrace、γ=4。保持 forward kernel、精度、数据、token budget、KV 总容量和输出语义一致。

| 变体 | 只改变什么 | 主要观察 |
|---|---|---|
| Full | 完整 FastSD | 参照 |
| w/o hetero priority | 移除硬件/网络/接受率等异构相关优先级，保留等待年龄和防饥饿 | 各类型等待、slowdown、公平性 |
| FIFO joint ablation | 全局 FIFO：联合移除多队列、队列间 WRR 和会改变顺序的优先级；保留 token budget、后端和必要依赖 | 长请求阻塞、短请求 TTFT；不能单独归因为多队列 |
| equal WRR | 6:3:1 改 1:1:1，其余不变 | 不同长度组的服务机会与尾延迟 |
| w/o KV prefetch | 保留同样卸载/容量政策，改为需要时搬运 | KV stall、命中率、PCIe 字节数 |

## 5.2.5 外部负载、服务容量与网络边界（E5）

### A. 开环负载扫描

固定 N=32、Hmix+Dmix、MixTrace、四方法。独立请求发生器按同一泊松到达轨迹提交；N 只限制 worker 处理能力，请求即使暂时没有空闲 worker，也要保留计划到达 a_i、排队和超时记录。

先用开发集估计 Standard SD 在此场景的稳定容量 λ_ref；所有方法共享 λ={0.25,0.50,0.75,1.00,1.25}×λ_ref，不按各方法自己的容量单独设置主比较负载。5×4×3 = **60 次**。

- 固定到达窗口建议 10 分钟，warmup 单独进行；具体时长按预实验冻结。
- 延迟按“窗口内到达的请求 cohort”跟踪到完成或统一超时；测量截止仍有请求必须记录为未完成，不能悄悄排除。
- 稳态吞吐按公共窗口内交付 token 计；固定 cohort 能耗则从首到达到最后完成/超时，分母用该 cohort 的成功输出。两者是不同口径，分栏记录，不能把含 drain 的能量除以不含 drain 的 token。
- 报告到达率、实际发出率、排队长度随时间、超时/拒绝率、排空时间及客户端积压。
- 能持续稳定服务的判断：队列没有持续发散，且在预先冻结的 TTFT/TPOT SLO 下满足完成率要求。SLO 用应用需求或开发集冻结的共同标准，写出数值后再跑正式数据，不按结果选 SLO。
- 若 λ=1.25λ_ref 仍未到 FastSD 拐点，追加已预先声明的逐级扫描，保留所有点，不能只选最优点。

### B. 资源与并发解耦

为避免将 E1 的 N 与 C 混为一谈，补一组固定 N=64、改变 C=16/32/64 的实验，使用同一资源池、同一请求轨迹和公平分配；记录实际活跃 worker。或固定 N=32，单独扫到达率（上面的 E5A 已覆盖）。两组的图题都说明是资源容量还是服务负载变化。

### C. 网络与异构比例（选做）

网络只在受控测试链路施加扰动，避免影响共享服务器管理流量。建议实际总 RTT 档位为原生值、20 ms、50 ms；设置的是目标“总 RTT”，记录真实 RTT，不把每方向增加值误写为 RTT。带宽主轨固定；带宽/丢包另作独立敏感性因素。

异构比例可在 N=32 下取 H1:H3=1:3、1:1、3:1，各节点内部仍 D1:D2=1:1；或固定 Hmix 调 D1:D2 比例。两种比例不要一次一起变。报告其资源放置变化，不将其视为完全相同机器的纯速度扰动。

第二 Target 只在 T1 核心结果完成后，选一种资源可承载且同样通过兼容验收的型号，重复 E1 的代表性场景与关键消融；不自动默认用户已确定第二 Target。

# 二、执行顺序、重复与统计

## 阶段 0：冻结和验收（E0）

按顺序完成以下检查，任何未通过项目对应的数据不得标为正式结果：

1. 冻结 T1/D1/D2、模型 revision、tokenizer、软件环境、GPU 配置、资源隔离与网络路径。
2. 跑单 Target 的最小生成；分别验收 H1D1/H1D2/H3D1/H3D2 的请求—draft—verify—回滚—终止流程。
3. 在共同 Target 配置上完成正确性与质量检查；确认 SpecEdge CPU 适配和 AR 服务入口的测量边界。
4. 单 worker 标定：相同 prompt/输出条件下记录 draft ms/token、γ 扫描、接受长度、通信、峰值内存、CPU/GPU 能耗可用性。
5. 逐步扩展 1→4→16→32→64，检查实例数、绑核、模型内存、队列和错误；该顺序仅为验收，不把它当成正式性能对照。
6. 校准 token budget、batch 上限、SpecEdge depth/budget、warmup、运行时长、超时和 SLO；记录候选范围与选择规则后冻结。
7. 用所有方法各跑一个小型统一 workload，确认时间单位、NA、总输出、失败数、总窗口、能量单位、JSONL 聚合一致。

## 阶段 1：最小可发表的实验集合

优先级：
- P0：E0；E1 总体性能及 E1-G 三重异构确认；E2 异构拆解；E3 γ；E4 机制消融。
- P1：E5A 负载扫描及尾延迟/公平性图。若论文强调 serving，应纳入核心结果。
- P2：网络敏感性、异构比例、第二 Target、thinking、精度/线程数扩展。

E1/E1-G/E2/E3/E4 的基础计划次数：108+36+54+36+36 = **270 次**；加入 E5A 为 **330 次**。330 不含关键条件增至 ≥5 次、KV 压力对照和追加负载点，因此不是总次数上限；也不是 330 次全新必跑：只有全部配置、请求 trace、随机种子和测量窗口口径完全一致时，才可复用交叉条件；单数据集 E1 不可直接替代 MixTrace 消融。

## 阶段 2：重复、顺序与异常

- 初始每条件 3 次独立运行，关键结论/高噪声条件至少 5 次。正式前用 pilot 估计方差和所需精度；“3 次”不是自动充足的统计证明。
- 配置相同的一组方法使用相同的数据顺序、请求 ID 与资源映射；开环另固定 arrival seed 和外生时间轨迹，闭环固定请求释放规则。方法执行顺序按重复平衡轮换，保存实际顺序。
- 模型加载后热身，等待显存/时延稳定；统一清理的是会话状态及缓存，不自动删除文件。禁止自动清空历史记录目录。
- 同一 run 中请求共享服务状态，不把它们当成完全独立的运行样本。置信区间按 run/原始题目分层，重放同一题目的相关性必须保留。
- 主要对比预注册为 FastSD 对 Standard SD、FastSD 对 SpecEdge；AR 是系统参照。做多个显著性检验时说明校正，但优先报告效应量及区间。
- 失败、OOM、超时、后台干扰各自分类并保留日志；统一规则决定是否无效/重跑。慢是有效结果，不能因为慢而删掉。
- 固定的全局 deadline 到达后，记录未完成与消耗的时间/能量，不使用成功子集均值掩盖失败。
- 若修改模型、代码、超参数、数据或测量口径，创建新的 protocol_version 和 run_id。

## 阶段 3：结果解释与写作检查

每个实验回答四句：改变了什么；其他条件如何固定；看到的绝对值与差异是什么；证据能支持什么、不能支持什么。

- FastSD 吞吐高但慢客户端 p95 更差：如实写出效率与公平性的权衡。
- 单核 CPU 起草成为瓶颈导致云端闲置：报告适用边界，不人为加大 γ 只让某方法受益。
- GPU-only 能量下降但 CPU 能量上升：讨论总能效，不只展示有利组件。
- 同质场景收益有限、异构下收益扩大：结合 E2/E4 与队列数据解释；不能仅靠一张总体柱图宣称异构贡献。
- 较长 γ 增加拒绝/验证浪费：通过实际候选和接受长度解释非单调变化。
- KV 预取在缓存完全驻留时无收益：这是合理边界，不能只留下高压力结果。
